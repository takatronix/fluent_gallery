## プロダクトの芯(1行)
**大量の画像を超高速・快適に「見る → 調整する → フィルタする → あの手この手で増やす →
データセットにする → LoRA/モデルを作る」までを一つの流れにする。**

## 原則: AI 1st(MCP前提)
**全ての操作はAIが外部から制御できることを前提に設計する**(ml-hubのMCP-first方針と同じ)。
- UIだけでできてAPIでできない操作を作らない(UIはAPIの1クライアントに過ぎない)
- MCPサーバとしてツール公開: search/ingest/enrich/dataset/genvar/edits/cache/presets/crawl…
- 「アスパラのデータセットを作って」の一言で、AIが 収集→属性付け→フィルタ→払い出し→(将来)LoRA学習
  まで自律実行できる粒度でツールを切る
- 判定は決定的に(同じ入力→同じ結果)、AI向けに件数/サイズ/所要見積りを常に返す

## アーキテクチャ
```
fluent_gallery (Rust, axum, 単一バイナリ, :8790)
├── web/            クールUI(WebGPU流体, スタッガ, モーフズーム)— 静的配信
├── store/          データの正本(このレイアウトは既に稼働中・変更しない)
│   ├── images/ab/<sha1>.<ext>   content-addressed本体(ハードリンク収蔵=容量ゼロ)
│   ├── meta/ab/<sha1>.json      サイドカー=正本(来歴/origin/VLM属性/edits)
│   ├── thumbs/                  webpサムネキャッシュ
│   ├── datasets/<name>/         払い出し(symlink+manifest)
│   └── index.sqlite             検索索引(サイドカーからいつでも再構築可)
│       ※単位=ライブラリ全体で1ファイル。データセット/ソース単位に割らない(横断フィルタが本命)。
│         テーブル: images(WHERE句に使う値だけ)/tags/captions(FTS5)/jobs(M3)/crawl_ledger(M5)。
│         WALモードで読み書き並行。原則「WHERE句に書く値だけDBへ、残りは正本のサイドカーへ」
├── engine/         GPU計算カーネル(Python:生成/学習)— ギャラリー自身のジョブキューが起動
│                   ※旧atelierへのHTTP依存は廃止。計算スクリプトだけを引き取る
└── 外部: ollama(:11434 内蔵VLM) / Claude·GPT API / ml-hub(:7000 データセットの客)
```
- **Rustが担う**: API/検索/収蔵(sha1/pHash)/サムネ/ジョブキュー/静的配信 — ML計算ゼロの領域
- **engineが担う**: t2i生成・img2img量産・(将来)LoRA学習。GPU譲り合いはエンジン側で完結
- Python版(legacy/)はAPI契約のリファレンス。UIは同一契約なのでそのまま動く

## API契約(Python版で実証済み、Rustが同一契約で置換)
収蔵: `POST /api/ingest {path,source,origin?,move?}` / サンプル取得(権利クリアな公開コレクション): `GET /api/samples`, `POST /api/samples/{id}?n=`(旧 presets は廃止 2026-09-04)
**まとめ取り(2026-09-04)**: n は最大20,000。源ごとの既読台帳 `store/samples/<id>.seen.json` にURLを残し、
次回はその続きから取る(同じ先頭を取り直さない)。API源はページを送りながら未取得がn件たまるまで掘る。
COCO は val2017 で足りなければ train2017 も開く(CC BY系のみ=全体の約1/4)。`POST /api/ingest/stop` で中断可。
検索: `GET /api/images?q&tag&source&origin&vlm_&scene&subject&style&nsfw&min_quality&limit&offset`
　　  `GET /api/facets` `GET /api/meta/{sha1}` `GET /img/{sha1}` `GET /thumb/{sha1}`
属性: `POST /api/enrich {backend,filter…}` `GET /api/enrich/status` `POST /api/enrich/stop`
払い出し: `POST/GET/DELETE /api/datasets(/{name})` `GET /api/datasets/{name}/shas`
増殖: `POST /api/genvar {shas,instruction,per_ref}`(エンジンのキューへ)
編集: `GET/PUT /api/edits/{sha1}`(履歴取得/push/pop/クリア) `GET /render/{sha1}?v=<rev>&w=`(履歴適用済み表示)
　　  `GET /preview/{sha1}`(1080段) — v はUI側キャッシュバスタ(サーバは常にファイルのrevが正)
保護: `POST /api/keep {shas,keep}` / アルバム: `POST/GET /api/albums` `DELETE /api/albums/{name}`
整理: `POST /api/prune {source,older_days,keep_quality,dry_run}`(→store/.trash、30日で自動空)
保守: `POST /api/rebuild` / `GET /api/cache/stats` / `POST /api/cache/clean`
　　  (サムネ・レンダ・一時_refs等の**キャッシュは全て再生成可能**なので、ワンクリックで安全に掃除できる)

## IA原則: 「探す」と「集める」を混ぜない(ml-hubの混乱の教訓)
- **🔍 検索 = ライブラリの中だけ**。検索バーは手持ちを絞る専用。外部へは一切行かない
- **📡 集める = 別ビュー**。外部獲得はソース別タブに集約:
  プリセット / Webクロール / X(Grok) / YouTube(動画→フレーム抽出、HDRトーンマップ必須) / 生成(genraw·genvar)
- どのソースも「注文→裏でジョブ→収蔵→ライブラリに現れる」の一方通行。
  検索結果に「まだ持ってない画像」が混ざることは決して無い

## 速さの設計(魔法の正体)
体感速度=魔法。原則「**画像が届く前に何かが見えている**」:
1. 多段サムネ(4段): **tint/ThumbHash(≈30B、API同梱→0msぼかし)** → **micro 96px(~3KB、星雲/数千枚俯瞰用)**
   → grid 360px → preview 1080px → 原寸。
   届いた順にぼかし→カリッと差し替え(iOS Photos感の正体)
2. **焼くのはgrid 360だけ**(ingest時・Rust+rayon並列、1枚20-30KB=グリッド速度の生命線)。
   preview 1080は初回表示時に生成してキャッシュ(+隣先読みで温める) — 全数焼くと100万枚で百GB級に
   膨らむため(→ディスク設計)。thumbhashはimagesテーブルに列で持つ
3. sha1 URLは内容不変 → `Cache-Control: public, max-age=31536000, immutable`(再訪時リクエストゼロ)
4. RustメモリLRUでホットサムネはディスクも読まない
5. DOM仮想化(見えてる分+バッファのみ。10万枚でもDOM数百 — ml-hub棚仮想化の教訓)
6. 先読み: スクロール方向prefetch+ライトボックス前後preload

## ディスク設計(大量前提の安全弁) — M4で実装済み
データは爆発的に増える前提。原則「**原本以外は全て上限つき再生成可能キャッシュ**」:
- 原本(store/images) — 同FSはハードリンク収蔵で容量ゼロ。sha1不変。これだけが本当に増える
  → 本丸はM7のS3/R2階層(hot=ローカルLRU/cold=R2)
- grid360サムネ — 小さい(20-30KB)ので常持ち・間引き対象外。100万枚でも~25GB
- preview1080(*.p.jpg) — オンデマンド生成、**LRU間引き対象**
- renders(非破壊調整のレンダ) — 履歴rev毎のキャッシュ。履歴が変わると即全破棄+**LRU間引き対象**
- **ジャニター常駐**: preview+renders合算を `FG_CACHE_MB`(既定20GB)以下に保つ。
  起動時+6時間毎に古い順(mtime)に間引き。/api/cache/stats が内訳と disk_free_gb を返す。
  ワンクリック全掃除(/api/cache/clean)も従来通り
- データセット払い出し=symlink(容量ゼロ)。ただし調整済み画像は焼き込みコピー(見た目通り渡すため)

### 原本の世代整理(prune) — 機械が集めた/作った古いデータは消してよい
「AIが作り続ける」前提では原本も無限に増える。人が入れたデータは消さない、機械のは間引く:
- `POST /api/prune {source, older_days, keep_quality=7, dry_run=true}` — source必須(全消し防止)
- **残るもの(保護の階層)**: ①⭐keep(「これは！」の明示保護、UI=S key/一括) ②VLM品質≥keep_quality
  ③データセット/アルバムが参照中 ④動的アルバムの現メンバー
- 消し方は即deleteでなく **store/.trash/d<day>/ へ退避** → 30日後にジャニターが空にする
  (ml-hubの教訓: 決定的な自動削除は控えめに・ゴミ箱経由)
- 常駐キュレーターは将来これをMCPで叩いて「収集→評価→間引き」を回す

### ⭐keep と アルバム
- **⭐keep** = 画像単位の「これは！」フラグ(sidecar正本+keep列)。pruneから絶対保護。UI: ライトボックス☆/S、選択バー一括、⭐フィルタ
- **動的アルバム**(store/albums/*.json) = 検索条件の保存。中身は常に「今」の検索結果=自動更新。
  メンバーはprune保護。UI: 絞り込み→「☆ 今の絞り込みを保存」
- **静的な入れ物**が欲しい時はデータセット払い出し(symlink=容量ゼロ)を使う — これも保護される

## AIフォルダ(エージェントフォルダ)構想 — 2026-09-02ユーザー発案、器はM4で実装済み
**「可愛い犬の画像」というフォルダを作る→エージェントが勝手に満たし続ける→
コピーして目標を「猫」に書き換えたら、独立した別エージェントとして動き出す。**

- **実体** = 動的アルバム + `goal`(自然言語の目標宣言) + `folder`(ネスト可)。
  コピー(⧉)=レシピ複製。目標/条件を書き換えるだけで増殖する。器・コピー・ツリーはM4実装済み
- **エージェントの有効性が見えること(必須)**: フォルダに状態バッジ
  🟢動作中 / ⏸待機 / 🔴エラー、最終稼働時刻、直近の収穫レート(24hで+N枚)、
  「調子」=ゲート通過率(取ってきた内どれだけ生き残ったか)。死んでるのに動いてるフリが一番ダメ
- **コストの見える化(必須)**: 画像1枚ごとにサイドカー `cost:{usd, by}` で獲得実費を記録
  (生成API/VLM判定/クロール従量)。索引cost列でフォルダ/ソース別に合算、UIに💸表示。
  **評価指標は「集めた枚数」でなく「生き残った良品1枚あたりのコスト」**(ゴミを金で買わない)。
  ml-hubのコストDS別計測と同思想、goal.yamlの実コスト同期の教訓を引き継ぐ
- **ゴミ対策が本体**(収集はゴミが9割、ml-hub collectで実証済み): 門前払いパイプライン
  DL検査→pHash近重複→CLIP/VLM意味ゲート(キーワード一致でなく目標の意味で判定)→quality閾値。
  自動削除は控えめ(フラグ→ゴミ箱経由、機械の即断で消さない)。既存の.trash/prune/keepが受け皿
- **呼び出すAIの構成(全部既存資産の流用)**:
  - 頭脳(計画/クエリ生成/満足判定) = Claude API(ml-hub collectのLLM再生成と同じ役)
  - 目利き(1枚ごとの意味ゲート) = 内蔵VLM qwen2.5vl(無料5s/枚)で門前払い→怪しい物だけClaude/GPTで再審(コスト階段)
  - 手足 = 本アプリのMCPツール群(search/ingest/enrich/genvar/prune/keep/albums…AI 1st原則の回収)
  - 生成 = engine(gpt-image-1/qwen)、収集 = M5クローラ/Xウォッチャー
  - 実行形 = Rust側は状態機械+ジョブキューだけ持ち、判断はLLM呼び出しに委譲(決定的な部分とAIの部分を分離)

## 教訓(引き継ぐ罠)
- claude系APIはthinkingブロックを返すことがある→content[0].text禁止、type=="text"を選ぶ
- pkill -f は自分のシェルを巻き添えにする(exit 144)→killはPID指定
- HDR動画の素朴8bit化は白飛び(ml-hub video_frames.py参照)
- VLM出力は固定スキーマで縛る+壊れJSONは1回だけ再試行
- **太いBLOBをimagesテーブルに入れない**(CLIP emb 2KB×13万で一覧が30倍遅化 → embs別テーブルへ分離)
- **ollamaはVRAM不足時にCPUへ部分オフロード**する(16コア占有でUIまで窒息)。
  診断=`curl 127.0.0.1:11434/api/ps` の size_vram/size、治療=`keep_alive:0`でアンロード→空きがある時に再ロード
- **削除と裏方AIの競合**: 削除直後の書き戻しで「原本の無い幽霊」が復活する → save_metaに原本存在ガード
- **UIの同じ状態を複数箇所が書くと必ず壊し合う**(ライトボックスで実証: 修正のたび別の退行)。
  表示の書き手は1人に集約し、回帰テストで守る
